# io-witness-shape-f

<!-- status: CONFIRMED -->

## Hypothesis

Two `@Witness` structs — `IO` (capability: read, write, close, ready) and `IORunner` (executor + shutdown) — plus a plain `IOBound` struct carrying both, compile cleanly on Swift 6.3 release. Both witnesses are `Sendable`, support `~Copyable` descriptor parameters, and the `@Witness` macro generates `unimplemented()` for each independently.

## Method

Compile-only sketch. The target is an executable that constructs an `IOBound` from `IO.unimplemented()` and `IORunner.unimplemented()` and prints confirmation.

Build command:
```bash
cd Experiments/io-witness-shape-f
swift build
```

## Result

**CONFIRMED** (Swift 6.3 release, macOS 26 arm64, 2026-04-17).

Build output:
```
[4/7] Write Objects.LinkFileList
[5/7] Linking io-witness-shape-f
[6/7] Applying io-witness-shape-f
Build complete! (1.27s)
```

Two `@Witness` structs (`IO`, `IORunner`) and the plain `IOBound` struct compile cleanly with `~Copyable` descriptor parameters, typed throws, and `Sendable` conformance. Both `unimplemented()` factories are generated by the macro. `public import Witnesses` is required (transitive `Standard_Library_Extensions.Result` case visibility); bare `import Witnesses` fails with "enum case 'success' is internal and cannot be referenced from an '@inlinable' function" under `InternalImportsByDefault`. Buffers use Sendable stand-ins (`ByteBuffer`, `MutableByteBuffer`) rather than `UnsafeRawBufferPointer` because the macro synthesizes `Sendable` closures around the witness surface and raw pointers don't conform.

## Analysis

If CONFIRMED, Shape F is viable as the public surface for `swift-io-primitives`. The `IOBound` composition point is a plain value struct with no new protocol or existential — consumers receive one `IOBound` value and dot into `.io` / `.runner` as needed.

Next verification (outside this sketch): confirm that `swift-witnesses`' composition helpers (`Witness.Recording`, `Witness.Scope`, `Witness.Values`) apply uniformly to both `IO` and `IORunner`.

## Migration to non-underscored storage

Re-verified 2026-04-16 against the updated `@Witness` macro which no longer imposes underscore prefixes on closure storage (and generates labeled sibling methods alongside labeled closure properties; zero-arg closures get no generated method per the V5 collision finding).

Changes:
- `IO.swift`: `let _read`/`_write`/`_close`/`_ready` → `let read`/`write`/`close`/`ready` (labeled closures; macro synthesizes sibling methods under the same name).
- `IO.Runner.swift`: `let _executor`/`_shutdown` → `let executor`/`shutdown` (zero-arg closures; call sites outside this sketch would invoke them as `runner.executor()` / `runner.shutdown()`).
- No manual forwarding extensions were present; none to delete.
- `main.swift` only constructs `.unimplemented()` and prints, so no consumer call sites required changes.

Build status: `swift build` succeeds on Swift 6.3 release, macOS 26 arm64.
