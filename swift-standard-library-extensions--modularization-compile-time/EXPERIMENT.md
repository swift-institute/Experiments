# Experiment: Modularization Compile-Time Impact

**Research handoff**: `../../Research/modularization-compile-time-impact.md`

**Status**: harness scaffolded; endpoints (N=1, N=max) pending first run.

**Toolchain**: Swift 6.3.1. Record machine/CPU/core count in `Outputs/machine.txt` before the first run.

## What this experiment measures

Wall-clock, CPU-seconds, frontend-stat, and binary-size differences for `swift build` on variants of `swift-standard-library-extensions` partitioned into N SwiftPM targets, holding source contents constant across N.

## Why a harness, not a one-file experiment

A benchmarking experiment cannot fit the one-`main.swift` shape of [EXP-003b]. The Swift target under `Sources/` exists only to satisfy [EXP-003d] naming alignment and to carry the header anchor. The actual experiment is the shell harness in `scripts/`, which operates on generated variant packages under `variants/`.

## Independent variables

| Variable | Levels | Notes |
|---|---|---|
| N (target count) | {1, 10, 40, max} | 1 = current baseline; max = one target per .swift file (≈87). 10/40 are arbitrary alphabetical partitions retained as *controls* for "N matters vs. partition-shape matters" — not recommendations. |
| Build mode | {debug, release} | |
| Scenario | {clean, incremental, consumer-only-Array, consumer-four-types, consumer-umbrella} | |
| @inlinable regime | {as-is, fully-annotated} | Only at N=max; no-op at N=1 |

## Controlled

- Source contents identical across N — only `Package.swift` and `Sources/` directory partitioning change. Achieved by symlinking canonical source files into generated variant directories.
- Toolchain 6.3.1.
- `rm -rf .build` between clean-build samples; verified gone (`! test -d .build`) before each build ([EXP-004]).
- Background load: user brings laptop to idle before a cell; close browser tabs, VSCode etc. Record ambient conditions in `Outputs/machine.txt`.

## Samples

Median-of-5 per (N × mode × scenario × regime) cell. Min/max recorded alongside. Full matrix is ~50 cells → ~250 samples; the MVP run (below) is a 4-cell subset.

## MVP — first clean signal first

Per [EXP-011a], structure the harness to produce one clean endpoint signal before scaling. The MVP answers: **does N=max debug clean build take 1.5×–4× N=1's time, or is it outside that range?**

MVP cells:
| N | Mode | Scenario | Regime |
|---|---|---|---|
| 1 | debug | clean | as-is |
| max | debug | clean | as-is |

If the MVP result is inside the predicted 1.5×–4× band, expand to the full matrix. If it's outside (e.g., N=max is 10× slower, or faster than N=1), re-read the result before expanding — it either invalidates the theoretical model or points at a harness bug.

## Scripts (contract)

**`scripts/generate-variant.sh <partition-file>`**
- Reads `partitions/<name>.txt` (each line: `<source-file> -> <target-name>`).
- Writes `variants/variant-<name>/Package.swift` with one `.target(...)` per unique target name, plus an umbrella target that depends on all of them and `@_exported public import`s them.
- Writes `variants/variant-<name>/Sources/<target-name>/<source-file>` as a symlink into the canonical `Sources/Standard Library Extensions/`.
- Idempotent: re-running regenerates.

**`scripts/run-sample.sh <variant-name> <mode>`** where mode ∈ {debug, release}
- `cd` into `variants/variant-<variant-name>/`.
- Ensures `.build/` does not exist (`rm -rf .build && ! test -d .build`).
- Runs `/usr/bin/time -l swift build [-c release]`, captures wall time and max-RSS.
- Appends one CSV row to `Outputs/samples.csv` with columns:
  `timestamp, variant, mode, scenario, regime, wall_seconds, user_cpu_seconds, max_rss_bytes, swift_version`.

**`scripts/run-mvp.sh`**
- Calls `generate-variant.sh` for `partition-1` and `partition-max`.
- Runs `run-sample.sh variant-1 debug` five times and `run-sample.sh variant-max debug` five times.
- Prints median wall time per cell.

## Interpreting results

The header-comment `Status:` field in `main.swift` is updated once MVP results return:

| MVP outcome | Status update | Next action |
|---|---|---|
| N=max debug clean within 1.5×–4× of N=1 | PARTIAL (endpoints within predicted band) | Expand to incremental + consumer scenarios |
| N=max debug clean outside 1.5×–4× | PARTIAL (endpoints outside predicted band) | Re-examine theoretical model or harness before expanding |
| Harness itself fails | ANALYSIS (harness bug) | Fix harness before measuring |

## Deferrals

These are out of scope for the MVP; they enter scope after MVP signal is clean:

- Intermediate N (10, 40) — useful only if MVP shows the endpoints are interesting.
- Release mode — requires separate runs; costs ~2× measurement time.
- Incremental builds — requires file-touch protocol and cache-warmed baseline.
- Consumer scenarios — require 3 additional SwiftPM packages under `consumers/`.
- `@inlinable` fully-annotated regime — requires a source-mutation pass. Only meaningful if MVP shows a measurable cross-module cost in release mode.
- Swift 6.4-dev nightly — secondary data point after 6.3.1 baseline is complete.
